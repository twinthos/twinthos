01 / THE POSITION

Don't trust the prompt.
Control the action.

A clever model can misread a document, follow a malicious instruction or use a tool incorrectly. The real protection has to exist outside the model's promises—in what the system is technically allowed to do.

01 / BOUND

Only the access a job needs.

Choose which accounts and actions it can use. Do not give it wider access just because it's easier.

LEAST PRIVILEGE
02 / APPROVE

A person makes the consequential call.

Define who may approve, which exact action they are approving, and when that approval expires. Guardian can return an “ask” decision; the current MCP demonstration does not include an approval interface or consume approval tokens.

HUMAN AUTHORITY
03 / RECORD

Be able to explain what happened.

Agree what actions are logged, what information is redacted, who can review the record and how long evidence is retained.

AUDITABLE ACTIONS
04 / CONTAIN

Assume something will go wrong.

Plan for prompt injection, a compromised integration, a bad answer or a failed alert. Document the stop, recovery and notification path.

02 / THE CONTROL PATH

The agent asks.
The host decides.

A model can request an action; it cannot be trusted to enforce its own permissions. A trusted host checks identity, policy and scope before calling a real tool. If a check fails, the operation never runs.

03 / PUBLIC ENGINEERING

Show the test.
Not a percentage.

Sentinel now demonstrates a narrow, read-only MCP execution boundary with real subprocess tests. It also offers offline, synthetic cloud-audit triage informed by ARTEX-era threats. Neither tool claims to secure all agent runtimes or monitor a live organisation. A model saying “denied” does not stop an unrelated tool.

04 / BEFORE DEPLOYMENT

Five answers you should
get in writing.

Policies are useful only when you know which real system, provider and person they apply to. These are the decisions each client deployment must make explicitly.

01What can the agent access and actually change?＋

List the named tools and accounts, allowable operations and which actions require explicit human approval. Avoid general claims such as “secure access to everything”.

02Where will our data go?＋

Document the specific cloud computer, model providers, data-processing locations, retention and training settings. We do not assume that using a UK-based computer means every supplier processes data in the UK.

03What stops one client seeing another's information?＋

Agree the isolation design, identity and credential management, access revocation, and how that separation is tested for the actual deployment.

04What is recorded, and what isn't?＋

Agree action logs, access to evidence, redaction of sensitive content, retention, export and deletion. A local hash-chained record is not the same thing as an immutable audit ledger.

05Who responds to a failure—or when we leave?＋

Specify incident escalation, notification responsibilities, recovery, rollback, credentials, record export and deletion on exit. Confirm them in the agreement before launch.
